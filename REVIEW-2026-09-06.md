## Security findings (frozen before optimization pass)

### Critical — 0

No critical issue was found.

### High — 2

#### H1. Paid model operations have no application-side request or output budget

- **Evidence:** `app/api/session/route.ts:14-64` mints a paid realtime client secret on every GET; `app/api/tool/route.ts:36-42` dispatches every POST; `lib/questions.ts:112-137,175-190` can make two question-generation calls; and `lib/embeddings.ts:14-32` makes paid embedding calls. None has a request-rate ceiling, and question generation does not set an output-token ceiling.
- **Exploit:** Anyone with the shared Basic Auth credential can script `/api/session` and the expensive tool names to create sustained OpenAI spend and exhaust provider quotas, making the study session unavailable. A stolen shared credential has the same effect.
- **Fix:** Add conservative process-local fixed-window limits before paid work, return HTTP 429 with `Retry-After`, and set a hard per-question output-token ceiling. A reverse-proxy or shared-store limit remains recommended for defense across processes and restarts.

#### H2. Several tool inputs and result counts are unbounded

- **Evidence:** `lib/tools.ts:9-58` accepts unlimited strings for names, queries, notes, question content, summaries, and paraphrases; `searchMaterialsArgsSchema` accepts any positive `k`; `app/api/tool/route.ts:9-12` accepts an unlimited tool name; and the parsed values reach paid embeddings (`lib/tools.ts:312-323,355-358`) or persistent SQLite writes (`lib/tools.ts:305-317,361-372`).
- **Exploit:** An authenticated caller can submit very large strings to consume memory, embedding budget, log/database space, or ask for the entire corpus in one response by setting a huge `k`.
- **Fix:** Put explicit maximum lengths on every server-dispatched string and cap material search results at five. Reject oversized tool names before they can be included in diagnostics.

### Medium — 3

#### M1. Diagnostic paths can transmit or persist student/corpus text

- **Evidence:** `lib/sentry-scrub.ts:43-49` deliberately preserves exception messages even though `app/global-error.tsx:12-14` and `instrumentation.ts:16` capture general errors. `lib/questions.ts:139-141` and `lib/embeddings.ts:25-27` copy the complete provider error body into local errors, which can then reach logs, `tool_errors`, or Sentry.
- **Exploit:** If a browser error includes a transcript or an OpenAI error echoes source material, that private text can be sent to Sentry or retained in plaintext diagnostics.
- **Fix:** Keep only exception types in Sentry and only provider/status identifiers in upstream errors. Cover both with sentinel tests.

#### M2. Authentication exists only in untracked nginx configuration

- **Evidence:** There is no application middleware/proxy or route authorization check. `docs/operations.md:62-66` says both public hosts rely on nginx Basic Auth and that the exact process start configuration is unverified.
- **Exploit:** A firewall, nginx, or process-binding mistake that exposes ports 3007/3008 would expose all student records, writes, and paid APIs without a second check.
- **Fix:** Add an application authentication/session layer and bind the Node processes to loopback, then verify the live nginx and firewall configuration. This requires deployment/auth design and is outside the brief's prohibition on deploy and credential changes.

#### M3. Oversized JSON is parsed before schema limits run

- **Evidence:** `app/api/tool/route.ts:19` and `app/api/transcript/route.ts:17` call `request.json()` before validation. Transcript fields are capped, but a transfer can still be much larger than the accepted object before parsing fails.
- **Exploit:** An authenticated caller can repeatedly send very large or deeply nested JSON bodies, forcing allocation and parsing before Zod rejects them.
- **Fix:** Enforce an nginx body limit and add a streaming byte-limited JSON reader in the app so chunked requests are also bounded. This is larger than a safe sub-30-line schema change and needs proxy alignment.

### Low — 3

#### L1. A transitive URL parser has high-rated published advisories

- **Evidence:** `npm audit --omit=dev --json` reported `fast-uri` 3.1.5 with four high-rated host-confusion/SSRF advisories; `package-lock.json:5714-5717` pins that version through peer build-tool paths.
- **Exploit:** No route was found that passes user URLs through this package, so a normal app user has no demonstrated path. A future build/config path that validates attacker-controlled URLs with the affected parser could misclassify the destination host.
- **Fix:** Refresh the lockfile to `fast-uri` 3.1.6 or later and confirm the production audit is clean.

#### L2. The application does not set browser hardening headers

- **Evidence:** `next.config.ts:4-9` has no `headers()` configuration. No Content Security Policy, anti-framing policy, content-type sniffing protection, or referrer policy is set in the repository.
- **Exploit:** This does not create script execution by itself, but it removes browser-level containment if a future rendering/sanitization defect appears and permits clickjacking when the nginx layer does not add equivalent headers.
- **Fix:** Add and browser-test a CSP compatible with Next.js/Sentry plus `frame-ancestors`, `X-Content-Type-Options`, and `Referrer-Policy`, or enforce and verify them at nginx.

#### L3. Corpus text is placed in the model's highest-priority prompt without an untrusted-data boundary

- **Evidence:** `lib/questions.ts:41-47,50-64` interpolates retrieved source material directly into the same system message as authoring instructions. Ingestion accepts local PDFs, but no web route uploads corpus files.
- **Exploit:** A malicious or contaminated locally ingested PDF can tell the question model to ignore authoring rules, degrading question integrity or causing unwanted reproduction of corpus text. A normal web user cannot add that PDF through this application.
- **Fix:** Put retrieved text in a separately delimited untrusted-data message, explicitly forbid following instructions found inside it, and add adversarial prompt tests. Structured output already limits the impact to question content.

## Optimization findings

_This pass began only after the security list above was frozen._

### O1. Vector retrieval materializes and fully sorts the corpus — recommendation

- **Trace:** `lib/rag.ts:85-98` selects every chunk including full text and embedding, converts and scores every embedding, sorts the complete array, and only then takes `k`. `lib/tools.ts:276-297` repeats the same full-array sort for all embedded mistake episodes.
- **Measurement:** A direct in-memory call to the production `searchMaterials` function with 64-dimensional test vectors took 7.66 ms for 1,000 rows, 11.86 ms for 10,000 rows, and 28.75 ms for 50,000 rows, while returning only five rows. Real embeddings are much wider, and the database must also allocate every row's text and embedding.
- **Recommendation:** Use a SQLite vector extension/index for corpus search. Until then, use a bounded top-`k` heap to remove the `O(N log N)` sort and avoid selecting full text until the winning row IDs are known. Do the same for episodic recall. Not implemented because choosing and deploying a vector extension is a data/deployment change, while a heap alone would not remove the dominant full scan.

### O2. Recording one result rebuilds the entire student profile — safe fix

- **Trace:** `lib/tools.ts:305-309` calls `recordResult`, then calls `getProfile(...).categories.find(...)` solely to return one updated mastery value. `lib/student.ts:97-152` shows that this performs five reads: all categories, a grouped scan of result errors, the latest session, recent misconceptions, and due categories, plus an in-memory sort.
- **Fix:** Return the already-calculated mastery from the write (`lib/student.ts:217`) and use it directly. This preserves the response exactly and eliminates unrelated queries from every answered question.

### O3. Every API call reopens SQLite and reruns schema checks — recommendation

- **Trace:** `app/api/tool/route.ts:36-42` and `app/api/transcript/route.ts:15-29` open and close the database for each request; `lib/db.ts:5-50` enables WAL, executes all `CREATE TABLE IF NOT EXISTS` statements, and runs two schema introspection queries on every open.
- **Measurement:** 1,000 in-memory `openDb`/close cycles took 97.54 ms (about 0.10 ms each) on this machine, which is small compared with OpenAI calls but unnecessary on local-only database operations.
- **Recommendation:** Split one-time migrations from connection opening and reuse one process-scoped connection with a deliberate shutdown/test strategy. Not implemented because connection lifetime under Next.js development reloads and production process management needs integration testing.

### O4. Existing batching avoids two likely hot-path problems — no change

- Transcript persistence already batches up to 20 lines and bounds the retry buffer at 500 lines (`app/page.tsx:25-30,251-278`). Embeddings already batch 100 inputs per provider call (`lib/embeddings.ts:3,13-32`). No N+1 provider call was found in those paths.
