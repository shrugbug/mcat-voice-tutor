# Generative UI / Adaptive Interfaces Landscape (August 2026)

Research survey for the MCAT voice study bot project. Current architecture: Next.js frontend, realtime voice agent (WebRTC), a `show_content` tool that renders sanitized HTML server-side. Question: what's beyond that for letting the agent reshape the study interface mid-session?

---

## 1. Vercel AI SDK — generative UI (streamUI/RSC → tool calling + client rendering)

**What it is:** The AI SDK (formerly "Vercel AI SDK") is the dominant TypeScript toolkit for building AI apps — ~11.5M weekly npm downloads, 23.7K+ GitHub stars, 614+ contributors as of April 2026. It has three layers: **AI SDK Core** (server-side generation + tool calling), **AI SDK UI** (`useChat`/`useCompletion` React/Vue/Svelte hooks), and **AI SDK RSC** (React Server Components streaming).

**How the UI actually gets generated — this has changed and matters for you:**
- The original "generative UI" pattern (`streamUI`, `@ai-sdk/rsc`) let a tool call *stream a React Server Component* straight from server to client — the model's tool call literally returned JSX that got rendered.
- **This path is now deprecated in practice.** Vercel's own docs mark AI SDK RSC development as **paused**, flag it experimental, and publish a migration guide off of it. AI SDK v6 (current, 2026) instead recommends: the model emits a **typed tool call** (JSON args, not UI code), the client's `useChat` stream delivers typed "UI parts," and **your own pre-built React components switch on tool/part type** to render. i.e., the LLM never generates UI code or JSX — it only selects/parametrizes components you already wrote. AI SDK v6 adds a `ToolLoopAgent` abstraction and a typed message-parts system built specifically for this pattern.

**Maturity/adoption:** Extremely mature and the most widely used layer of the stack; this is the "boring, safe" default for JS/TS shops. RSC-based streaming JSX is a maintained-but-frozen dead end.

**License:** Apache 2.0 (open source), Vercel-maintained.

**Link:** https://ai-sdk.dev · https://vercel.com/blog/ai-sdk-6 · migration-off-RSC docs at https://vercel.com/templates/next.js/rsc-genui

## 2. thesys C1 (c1.thesys.dev)

**What it is:** "The first Generative UI API" — an OpenAI-compatible model endpoint plus a React runtime SDK. Instead of returning markdown/plain text, C1 returns UI.

**How the UI actually gets generated:** Three-stage pipeline: (1) your backend/model response is sent through the C1 API; (2) C1 returns a proprietary **JSON-based DSL** describing UI components (a typed UI schema, not raw HTML or JSX); (3) the **C1 React SDK** (`<C1Component>`, `<C1Chat>`) interprets that DSL client-side and renders it as live React components, managing state/updates/error handling. Supports forms/inputs, chained actions (trigger API calls, update UI), and custom actions bound to your own functions.

**Maturity/adoption:** Launched publicly April 2025 (per BusinessWire). Has a hosted console (console.thesys.dev), a documented pricing model (LLM tokens billed pass-through + Thesys API-call quota; e.g., a separate Reports API gives 100 free pages/mo then $0.01/page), and a startup program. Vendor-hosted product, not a widely-adopted open standard yet — smaller ecosystem than Vercel AI SDK or CopilotKit.

**License:** The core C1 API/DSL runtime is a **closed, commercial, hosted product**. Thesys has separately open-sourced a related project, **OpenUI** (`thesysdev/openui` on GitHub) — "the open standard for generative UI," MIT-licensed judging by the repo, with its own compact streaming DSL ("OpenUI Lang," claimed ~67% fewer tokens than JSON) and a renderer-agnostic React runtime. OpenUI is worth evaluating separately from commercial C1 if you want the DSL-interpreter pattern without vendor lock-in.

**Links:** https://www.thesys.dev · https://docs.thesys.dev · https://www.thesys.dev/pricing · OpenUI: https://github.com/thesysdev/openui , https://www.openui.com

## 3. CopilotKit generative UI (docs.copilotkit.ai)

**What it is:** "The frontend stack for agents" — a React (also Angular/mobile/Slack) SDK for building in-app AI copilots with chat UI, headless UI, and generative UI. CopilotKit is also the creator of **AG-UI**, an open protocol for agent↔frontend communication that has been adopted/referenced by Google, Microsoft, Amazon, and Oracle per CopilotKit's own materials.

**How the UI actually gets generated:** Same fundamental pattern as AI SDK v6's current recommendation: **you register real React components** (`useCopilotAction` with a `render` function, or the newer generative-UI hooks), the agent calls a tool/action, and CopilotKit maps that tool call to your pre-registered component with the returned args as props. No UI code or DSL is generated by the model — it's component *selection + parametrization*, streamed over AG-UI's event protocol (state deltas, not full re-renders). Also supports "human-in-the-loop" patterns — render an approval/edit UI mid-agent-run before continuing.

**Maturity/adoption:** Actively developed, 34K+ GitHub stars as of mid-2026, has a paid "Enterprise Intelligence" tier on top of the OSS core. AG-UI protocol has an independent GitHub org (`ag-ui-protocol/ag-ui`) suggesting it's positioning as a cross-vendor standard, similar in spirit to MCP but for the agent-to-frontend leg.

**License:** MIT (both CopilotKit core and AG-UI protocol).

**Links:** https://docs.copilotkit.ai · https://github.com/copilotkit/copilotkit · https://www.copilotkit.ai/ag-ui · https://github.com/ag-ui-protocol/ag-ui

## 4. Google/DeepMind "Generative UI" research

**What it is:** Google Research published a 2025 paper, **"Generative UI: LLMs are Effective UI Generators"** (arXiv, foundational case for *unconstrained* UI generation — i.e., not picking from a fixed component library, but having the model write bespoke UI per prompt). Related follow-on work includes **AlignUI** (arXiv 2601.17614), on aligning LLM-generated UIs with user/design preferences.

**How the UI actually gets generated:** Full **agentic code generation** — the model (Gemini 3-class) plans the response, writes actual UI code (HTML/CSS/JS or a web app), and stitches it into a working interactive interface *per query*, not from a fixed component palette. This shipped as a real product feature: **"Dynamic View"** in the Gemini app, and generative UI in Google Search's **AI Mode**, where a custom visual layout (interactive tools, simulations, grids, tables, images) is coded on the fly for each search query.

**Maturity/adoption:** This is the most production-scale deployment of "true" (code-generating, not component-slotting) generative UI — live in Google Search AI Mode and the Gemini app as of late 2025/2026. It is Google-internal infrastructure (agentic coding + presumably a sandboxed execution/render environment); no public SDK for third parties to replicate the exact pipeline. Directionally important as evidence the "model writes real UI code live" approach is viable at consumer scale, but not something you can adopt directly — it validates the *idea*, not a tool you can install.

**Links:** paper: https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/ · product: https://blog.google/products-and-platforms/products/search/gemini-3-search-ai-mode/ · Google Cloud explainer: https://cloud.google.com/discover/generative-ui

## 5. Ink & Switch — malleable software (Patchwork, Embark, Potluck)

**What it is:** A research lab essay/project line, not a product. **"Malleable Software: Restoring User Agency in a World of Locked-Down Apps"** (Geoffrey Litt, Josh Horowitz, Peter van Hardenberg, Todd Matthews, 2025) is the manifesto: end users, not just developers, should be able to reshape the tools they use, with AI lowering the cost of small bespoke tweaks. Concrete projects in this line: **Patchwork** (version control for writing/software built on Automerge/local-first CRDTs, 2024–2026), **Embark**, and **Potluck**.

**How the UI actually gets generated:** This is architecturally the *opposite* pole from thesys/CopilotKit: rather than an agent streaming components into a fixed chat surface, the philosophy is that **the underlying data lives in user-owned, versionable documents (Automerge CRDTs)**, and both AI and humans can fork/branch/edit the *software itself* (not just its output) over time, with full history/rollback — closer to "AI-assisted live software editing with git-like semantics" than "agent renders a widget."

**Maturity/adoption:** Research-stage, not a shippable SDK. No enterprise adoption; primarily influential as a design-philosophy reference point (frequently cited by Simon Willison and others in the LLM-tooling community) rather than infrastructure you'd depend on. Useful as a mental model — "let the user/agent reshape the actual app over a session, with reversibility" — even if you don't adopt Automerge.

**Links:** https://www.inkandswitch.com/essay/malleable-software/ · https://www.inkandswitch.com/project/patchwork/ · Geoffrey Litt's newsletter: https://buttondown.com/geoffreylitt

## 6. MCP Apps / MCP-UI — interactive UI over the Model Context Protocol

**What it is:** A now-**official** MCP extension for servers to ship interactive UI alongside tool calls. Originated as the community **mcp-ui** project (Ido Salomon + Liad Yosef, `idosal/mcp-ui` on GitHub) and was merged with OpenAI's Apps SDK concepts into a joint proposal.

**Timeline (verified, moves fast):**
- Nov 21, 2025 — proposed as **SEP-1865** ("MCP Apps: Interactive UIs Become an Official Part of MCP"), explicitly co-authored/backed by Anthropic, OpenAI, and the MCP-UI maintainers.
- Jan 26, 2026 — shipped as the **first official MCP extension**.
- Jul 28, 2026 — folded into the locked-down **2026-07-28 MCP specification**.

**How the UI actually gets generated:** Servers **pre-declare UI templates as MCP resources** using a `ui://` URI scheme, referenced from tool metadata. This means the UI is *not* generated live by the model per-turn — it's authored ahead of time by the server developer (HTML/JS you write), and the model's tool call selects/parametrizes which pre-registered UI resource to invoke and with what data. The declared HTML is rendered by the **host** (e.g., Claude, ChatGPT, or any MCP client) in a **sandboxed iframe**. The UI-to-host communication reuses the **existing MCP JSON-RPC protocol over `postMessage`**, so every UI-triggered action (e.g., a button click that should call back into the agent) goes through the same audit/consent path as a normal tool call — no bespoke messaging layer, no new trust boundary to design from scratch.

**Maturity/adoption:** Real and current — not vaporware. Adopters cited by the MCP blog include Postman, Shopify, and Hugging Face. It's a security-conscious design specifically because the sandboxed-iframe + JSON-RPC-only-communication pattern was built to prevent exactly the class of XSS/prompt-injection-via-UI risk you'd worry about with a `show_content`-style raw-HTML tool. Still early relative to install base (client support for rendering `ui://` resources varies by host), but it is the closest thing to an emerging cross-vendor standard for "agent tool call → interactive widget," and it's protocol-native rather than framework-specific — relevant since MCP is presumably already (or could be) your tool-calling substrate.

**License:** The MCP specification itself is open (MIT-style, per the modelcontextprotocol.io org); `idosal/mcp-ui` is open source (Apache-2.0-family — verify current LICENSE file at time of adoption).

**Links:** spec text: https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx · announcement: https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/ · "now official": https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/ · community SDK: https://github.com/idosal/mcp-ui · current spec: https://modelcontextprotocol.io/specification/2026-07-28

## 7. Other notable projects

- **OpenUI** (`thesysdev/openui`) — MIT, open-source sibling to commercial C1. Renderer-agnostic, compact streaming DSL ("OpenUI Lang", claimed ~67% fewer tokens than an equivalent JSON schema) interpreted by a React runtime. Four building blocks: a component **Library** (Zod schemas + React renderers = the contract between your app and the model), a **Prompt Generator** that turns the library into a system prompt teaching the LLM valid OpenUI Lang syntax, a **streaming parser**, and a React renderer. Directly comparable to AI SDK v6/CopilotKit's "component registry + model selects" pattern, but with a formal typed DSL instead of ad hoc tool-call JSON. Repo: https://github.com/thesysdev/openui, docs: https://www.openui.com/docs/openui-lang/overview
- **CopilotKit/OpenGenerativeUI** — CopilotKit's own open-source generative-UI framework repo (separate from the main CopilotKit package); worth a look if evaluating the CopilotKit ecosystem specifically. https://github.com/CopilotKit/OpenGenerativeUI
- **llm-ui** (`llm-ui.com`) — a smaller React library focused on smoothly rendering/streaming LLM output (markdown, code blocks) into React, not full component-generation — more adjacent than competitive, useful if you just need clean incremental-text rendering.
- **awesome-generative-ui** (`narrowin/awesome-generative-ui` on GitHub) — a curated, actively-updated list covering this entire space; good bookmark for staying current as it moves month to month.
- **Anthropic Claude Artifacts (2026 state)** — Artifacts has grown from a static preview pane into a platform: persistent storage across sessions, artifacts that can call the Claude API directly ("intelligent micro-apps"), MCP-integration hooks (Calendar/Gmail/Slack), and — per Anthropic's 2026 announcements — **generative UI widgets** (sliders, charts, animations) rendered inline in conversation. This is closed, claude.ai-hosted infrastructure, not an SDK for embedding in a third-party Next.js app, but it's the same underlying idea (agent emits structured UI, host renders it in a sandbox) and confirms Anthropic is investing in the pattern generally — relevant context for where MCP Apps (item 6, which Anthropic co-authored) is headed.

## Fit for a voice MCAT study bot

Ranking the approaches most suited to letting a realtime voice agent reshape a Next.js study interface mid-session, beyond the current `show_content` (server-rendered sanitized HTML) baseline. Criteria: latency (voice needs fast turnaround), security (sandboxing of AI-generated UI), implementation complexity for a small team, and fit with an existing tool-calling architecture.

### 1st — Component registry + typed tool calls (AI SDK v6 pattern / CopilotKit pattern), NOT streamed code
This is the lowest-risk, highest-leverage next step and is really an evolution of what you already have rather than a new architecture. You already dispatch tool calls from the voice agent; the change is to stop rendering a single generic `show_content(html)` tool and instead register a **small library of purpose-built React components** (flashcard deck, passage+question panel, progress ring, timer, diagram viewer, formula sheet) that tools can invoke with typed JSON args — exactly the pattern AI SDK v6 now recommends after abandoning streamed-RSC generative UI, and exactly what CopilotKit's `useCopilotAction`/AG-UI does. Latency is excellent (no extra network hop or DSL-interpretation step — it's a normal tool-call round-trip your voice pipeline already does; component render is instant client-side). Security is by construction: the model never emits HTML/JS, only parameters into components you wrote and control, so there's nothing to sanitize beyond ordinary prop validation. Implementation complexity is low-to-moderate: build/maintain a component library once, expand it incrementally as new study-interface needs appear. It fits your Next.js + tool-calling stack directly — you could adopt either the AI SDK's UI-parts pattern or CopilotKit wholesale, or just hand-roll the same idea (tool name → component map) without adopting either library, since the pattern itself is the valuable part.

### 2nd — MCP Apps / MCP-UI (`ui://` resources in sandboxed iframes)
Worth adopting if your tool-calling substrate is (or will become) MCP-based, or if you want a standardized, cross-client answer rather than a bespoke component map. It upgrades your current `show_content` almost directly: instead of raw sanitized HTML injected into the page, you pre-author HTML/JS "UI resources," declare them via `ui://` URIs, and let the host render them in a **sandboxed iframe** with all interaction routed back over the existing MCP JSON-RPC/postMessage channel — meaningfully more secure than sanitize-and-inject-HTML because the sandbox boundary and the communication channel are both protocol-enforced rather than something you have to get right yourself. Latency is good but not as tight as pattern #1 — iframe creation/postMessage handshake adds a small but real overhead versus a native React re-render, which matters more for voice (every turn should feel instant) than for a chat UI. Complexity is moderate: you're adopting a real spec (folded into MCP as of the 2026-07-28 release) and its SDK rather than hand-rolling, which is less work than building your own protocol but more than just writing React components. Recommended as the second step once the component-registry approach (#1) proves out which widgets you actually need — MCP Apps is the right target if this bot's tool layer is already/becomes MCP, or if you want portability across future MCP-based hosts beyond your own Next.js app.

### 3rd — Constrained UI DSL interpreted client-side (OpenUI / thesys C1 pattern)
A middle ground between "model only picks from fixed components" (#1) and "model writes arbitrary code" (Google's Dynamic View) — the model emits a structured, typed UI description (not code) that a renderer interprets into a bounded set of component primitives. This buys more per-turn compositional flexibility than a fixed component registry (the agent can, e.g., assemble a two-column layout with a chart plus three inline flashcards without you having pre-built that exact composite) while remaining far more sandboxable than raw HTML, since the DSL vocabulary is closed and validated before rendering. The tradeoff against #1 and #2: it's a genuinely new piece of infrastructure to build or adopt (a parser/renderer, a constrained grammar, prompt-engineering to keep the model inside it) — commercial C1 removes that build cost but adds vendor lock-in and per-call cost on a system that's also paying for realtime voice tokens; OpenUI removes the lock-in but you'd be maintaining the DSL/runtime yourselves. For a small team, this is worth revisiting only if the fixed-component approach (#1) turns out too rigid in practice — start there, and reach for a DSL layer only if you find yourselves wanting compositional flexibility a static component library can't give you.

**Not recommended as a near-term direction:** RSC-streamed generative UI (Vercel's original `streamUI`, now paused/deprecated — don't build on a frozen path) and Google's full agentic-code-generation approach (Dynamic View) — the latter is compelling evidence for where the field is headed, but it requires sandboxed live-code-execution infrastructure at a scale/security posture far beyond what a small team should take on for a study app, especially under voice-interaction latency constraints.
